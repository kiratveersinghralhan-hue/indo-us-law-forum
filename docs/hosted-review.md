## Environment and access

`render.yaml` contains only non-secret settings. Set `VITE_SUPABASE_PUBLISHABLE_KEY` through Render's environment prompt (`sync: false`), using the existing dedicated project's publishable key from the ignored local configuration. Do not paste credentials into chat or commit environment files. `VITE_DATA_MODE=supabase` and `VITE_SUPABASE_URL=https://erwliwgbjlutczmtqoss.supabase.co` are explicit. The publishable key is intentionally browser-visible; it is not a privileged credential. Never supply a database password, access token, secret/service-role key or an additional `VITE_*` secret. `.env.example` remains unchanged and placeholder-only.

`build:review` validates the browser environment before building; `start:review` rejects mock mode, other projects, privileged/placeholder keys, unexpected public variables, insecure or mismatched origins and invalid ports. It uses Render's [automatic `RENDER_EXTERNAL_URL`](https://render.com/docs/environment-variables) as the canonical review origin; `PUBLIC_SITE_ORIGIN` is only needed for explicit local smoke testing. It does not load local dotenv files on the host. The build still uses Vite's normal environment resolution; actual environment files must remain excluded from Git.

`SITE_INDEXABLE=false` is enforced. Every application response, including sitemap, fonts, media and errors, carries `X-Robots-Tag: noindex, nofollow`; public HTML keeps noindex metadata and robots disallows crawling. **Noindex does not make the site private.** Anyone with the URL can inspect published content. No HTTP password gate was added. Provider-generated cold-start/error pages bypass Node and need hosted inspection; app headers cannot guarantee their headers. Free Render supplies disallow-all robots while sleeping.

Staff access stays behind existing Supabase Auth and active staff permissions. Anonymous SSR ignores visitor cookies/Authorization and uses the dedicated publishable configuration; content queries and existing RLS expose only published records. Authorized admin edits on the review site will affect the **same dedicated backend**, not a separate staging database. Do not use review access to create test public content or grant Dilraj staff permissions implicitly. No fictional authors/articles/cases are added; missing published content retains honest empty states.

Submission and notification policy gates remain hard-disabled in the existing shared policy source, and analytics remains disconnected. No new server, Edge Function, recipient or tracking configuration enables them. Existing recovery UI remains available, but this task sends no recovery email. Once the actual temporary URL exists, review the dedicated project's [Auth redirect allowlist](https://supabase.com/docs/guides/auth/redirect-urls): add only the exact `https://ACTUAL_REVIEW_HOST/admin/recovery` if separately approved, preserving local entries and existing Site URL.
